# AEMET Antarctic Weather API

A small full-stack project that retrieves historical weather data (temperature,
pressure, wind speed) from AEMET's two Antarctic meteo stations — **Gabriel de
Castilla** and **Juan Carlos I** — through a local REST API with SQLite
caching, plus a React/TypeScript dashboard to browse the data. Built for the
GS Inima Development Challenge (wind-farm feasibility study in Antarctica).

```
aemet-project/
├── backend/     FastAPI service + SQLite cache (Parts 1 & 2)
└── frontend/    React + TypeScript dashboard (Part 3)
```

## Quick start

### Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env        # then edit .env and paste your AEMET_API_KEY
uvicorn app.main:app --reload
```

The API is now at `http://localhost:8000`. Interactive docs (Swagger UI) at
`http://localhost:8000/docs`.

Run the tests:

```bash
pytest -v
```

### Frontend

```bash
cd frontend
npm install
cp .env.example .env        # defaults already point at http://localhost:8000
npm run dev
```

Open `http://localhost:5173`.

### Getting an AEMET API key

Request one at https://opendata.aemet.es/centrodedescargas/inicio using a
**personal** e-mail address — AEMET has been observed to block requests from
corporate/company domains.

## Part 1 — The API

### Endpoint

```
GET /api/antartida/datos/fechaini/{fechaIniStr}/fechafin/{fechaFinStr}/estacion/{identificacion}
```

| Parameter | Where | Values |
|---|---|---|
| `fechaIniStr`, `fechaFinStr` | path | `YYYY-MM-DDTHH:MM:SS` |
| `identificacion` | path | `Meteo Station Gabriel de Castilla` \| `Meteo Station Juan Carlos I` (URL-encoded) |
| `location` | query, optional | IANA timezone (`Europe/Berlin`) or fixed offset (`+02:00`) that `fechaIniStr`/`fechaFinStr` are expressed in |
| `time_aggregation` | query, optional | `none` (default) \| `hourly` \| `daily` \| `monthly` |
| `data_types` | query, optional, repeatable | `temperature`, `pressure`, `speed`. 0–3 values; **empty = all three** |

Example:

```
GET /api/antartida/datos/fechaini/2024-01-01T00:00:00/fechafin/2024-01-03T00:00:00/estacion/Meteo%20Station%20Gabriel%20de%20Castilla?time_aggregation=daily&data_types=temperature
```

Full interactive reference (request/response schemas, try-it-out) is
auto-generated by FastAPI at `/docs`, so it isn't duplicated by hand here.

### Output timezone & the DST requirement

Per the spec, the output `datetime` field is **always** Europe/Madrid
(CET/CEST) with an explicit UTC offset, regardless of what `location` the
request used for input. This is deliberately a *different* timezone concern
from `location` (see the docstring in `app/timezone_utils.py`):

- `location` only affects how the **input** range is interpreted before
  querying.
- Europe/Madrid always governs the **output** representation and, crucially,
  the day/month boundaries used for `daily`/`monthly` aggregation.

**Confirmed DST behaviour** (see `tests/test_timezone_utils.py` and
`tests/test_aggregation.py`):

- A reading's offset in the output is `+01:00` (CET) in winter and `+02:00`
  (CEST) in summer — resolved automatically via Python's `zoneinfo`
  (`Europe/Madrid`), which reads the official IANA rules rather than a
  hardcoded offset.
- `daily`/`monthly` aggregation buckets by the **Madrid calendar day/month**,
  not the UTC one. Example: `2024-01-01T23:30:00Z` is already
  `2024-01-02T00:30:00+01:00` in Madrid, so it is correctly counted towards
  Jan 2nd, not Jan 1st. Near the spring/autumn DST transition, a "day" can
  therefore be 23 or 25 hours of UTC-time wide — this is intentional and
  matches how a human in Madrid would read the resulting report.
- We use `zoneinfo` instead of `pytz` deliberately: `zoneinfo` resolves DST
  automatically whenever a timezone is attached to a datetime, avoiding the
  classic `pytz` foot-gun of forgetting to call `.localize()`/`.normalize()`
  around arithmetic.

### AEMET's two-step API

Every AEMET OpenData endpoint (including `antartida`) returns a small JSON
envelope pointing at a temporary `datos` URL, which must be fetched
separately for the actual payload. This is implemented once in
`app/aemet_client.py`, isolated behind a small interface so it's the only
place that needs to change if AEMET's contract changes, and so it can be
swapped for a fake in tests instead of hitting the network.

Retries with exponential backoff (`tenacity`) cover transient 5xx/429/network
errors — AEMET publishes a 50 requests/minute rate limit, so 429s are a
realistic occurrence once several consumers share one deployment.

## Part 2 — Caching with SQLite

### Data model

- `measurements`: one row per `(station, timestamp)` **raw 10-minute
  reading** — the finest granularity AEMET provides. Hourly/daily/monthly
  views are computed on read, so no information is ever lost to
  pre-aggregation, and adding a new aggregation window later needs no schema
  change.
- `fetch_log`: one row per station recording the span of data already held
  locally (`earliest_datetime_utc` → `latest_datetime_utc`) and when it was
  last checked against AEMET.

### Cache strategy 

AEMET only publishes new Antarctic readings a few times a day, but the brief
describes traders polling far more often for intraday decisions. Re-fetching
the whole requested range on every call would be slow and would risk the
50 req/min AEMET limit once "thousands of requests" are in play. Instead, on
each request (`app/cache_service.py::ensure_data_cached`):

1. **Cold cache** for a station → fetch the whole requested range from AEMET.
2. Requested range starts **before** what we've ever fetched → also fetch
   that missing "left" slice (handles first-time historical queries).
3. Requested range extends **beyond** the latest data we hold, *or* our data
   hasn't been re-checked in `CACHE_TTL_MINUTES` (default 30) → fetch the
   missing/possibly-updated "right" slice, since that's where AEMET appends
   new readings.
4. Otherwise → served **entirely from SQLite**, zero calls to AEMET.

Rows are **upserted** by a `(station_id, datetime_utc)` unique constraint, so
re-fetching an overlapping slice is idempotent and safe to retry.

This is intentionally *not* a general-purpose interval tree over arbitrary
gapped ranges — for a genuinely append-mostly timeseries like this one, that
would be solving a harder problem than the data shape requires. If AEMET
started back-filling arbitrary historical gaps, this would be the first
piece to revisit.

### Logging

`app/logging_config.py` sets up single-line, greppable logs
(`timestamp | level | logger | message`) with a configurable `LOG_LEVEL`.
Every AEMET call, cache decision, and error is logged with enough context
(station, range, row counts) to troubleshoot a "why is this data stale/
missing" report without reproducing the request.

### Towards scalability 

The potential scalibility of this product that could be performed:

- **SQLite → Postgres**: SQLite is perfect for this challenge's scope (single
  process, low write concurrency due to the Antarctic data is small). At real
  multi-instance/high-write scale, swapping `DATABASE_URL` for Postgres is a
  one-line config change since the code only uses SQLAlchemy, no
  SQLite-specific SQL.
- **Concurrent cache refresh**: today, the DB session and `ensure_data_cached`
  call happen inline on the request path. Under real load this would move to
  a background refresh (e.g. a scheduled job hitting AEMET every few minutes
  per station, independent of request traffic), so no user request ever pays
  the AEMET round-trip latency, and the read path becomes pure SQLite.
- **Rate-limit coordination across instances**: if this API is horizontally
  scaled, multiple instances polling AEMET independently could collectively
  exceed the 50 req/min limit. A shared lock/token bucket 
  would coordinate that.

## Part 3 — Frontend

A small React + TypeScript (Vite) dashboard: a query form (station, date
range, input timezone, aggregation, measurement checkboxes) plus a line chart
and a table rendering the response. No extra backend endpoints were needed —
the same `/api/antartida/datos/...` endpoint powers the UI.

Notes on the implementation:

- Typed end-to-end: `src/types.ts` mirrors the backend's Pydantic schemas by
  hand (no code generation), works well at this size;
- `recharts` was used for the chart in order to have chart axes and spend time on the correctness of the data/timezone.

## Testing

`backend/tests/` covers, with `pytest`:

- **`test_timezone_utils.py`** — input timezone parsing (IANA + fixed
  offset), UTC conversion, and the DST behaviour described above (including
  the exact spring-forward transition instant).
- **`test_aggregation.py`** — none/hourly/daily/monthly bucketing, the
  Madrid-vs-UTC daily-boundary edge case, and the `data_types` filter.
- **`test_aemet_client.py`** — the two-step AEMET call flow, no-data (404),
  and server-error/retry behaviour, mocked with `respx` (no real network
  calls).
- **`test_api.py`** — end-to-end endpoint tests via FastAPI's `TestClient`,
  with the AEMET client and DB swapped for fakes/an in-memory SQLite DB via
  dependency overrides; covers validation errors (bad date format, unknown
  station, `start >= end`) and the cache-hit-avoids-a-second-AEMET-call
  behaviour from Part 2.

This isn't exhaustive (see **Known limitations** below) but is meant to
demonstrate the testing *approach*, per the brief's "even if they do not
cover every possible scenario."

## Known limitations / TODOs

Left out for time, flagged here rather than silently skipped:

- No authentication/authorization on the API — out of scope for the
  challenge, but would be required before "thousands of internal
  applications" actually consume this in production.
- No pagination on the `data` array — fine for the data volumes a single
  station/range produces here, but a real high-frequency consumer would want
  cursor-based pagination.
- The frontend chart renders one axis for all selected measurements
  (temperature/pressure/speed share a single Y scale); a production version
  would use per-series axes or small multiples.
- No Docker/Compose setup — the two services are simple enough to run
  locally as documented above; containerizing both would be a natural next
  step for deployment.
- `FetchLog`/cache strategy assumes a single, append-mostly stream per
  station (see the caching section above) — it does not handle AEMET
  retroactively revising already-fetched historical values beyond a normal
  upsert on the next overlapping fetch.
